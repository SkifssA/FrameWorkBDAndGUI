# Соглашение об именовании файлов в модуле

Действует для всех модулей в каталоге `module/<mod>/`. Ядро (`core/`) этим правилам
не подчиняется — оно, наоборот, опирается на них при генерации кода
(`core/createClass/bildersClass/*`) и при динамическом диспетчинге
(`ActionDispatcher.action()` выводит имя пакета модуля из префикса класса).

---

## 1. Три обязательных уровня имени

Любой файл логики/интерфейса модуля называется по схеме:

```
<PREFIX>_<ObjectName><Role>.py
   │        │         │
   │        │         └── Роль (суффикс): Logic | Pub | Dpi | Dvi | Pkg
   │        └──────────── Имя объекта: PascalCase, единственное число
   └───────────────────── Префикс модуля: 2–4 буквы, Title-case (Awh, Bc)
```

Примеры: `Awh_AnimeLogic.py`, `Awh_AnimeGenreDvi.py`, `Bc_ScriptSchedulerPkg.py`.

Правила:
- **Префикс** совпадает с именем папки модуля, но пишется в регистре как задумано
  (`module/awh/` → `Awh_`, `module/bc/` → `Bc_`). Он уникален в проекте и
  зарезервирован за модулем навсегда.
- **Разделитель** — одно подчёркивание после префикса. Внутри имени объекта и
  перед ролью подчёркиваний нет: `Awh_AnimeGenreLogic.py`, а не `Awh_Anime_Genre_Logic.py`.
- **Имя файла = имя главного класса в файле**, символ в символ. Проверяется грепом:
  `grep -c "class Awh_AnimeLogic" object/anime/Awh_AnimeLogic.py`.

## 2. Роли (суффиксы)

| Суффикс | Расшифровка | Назначение | Кто пишет |
|---|---|---|---|
| `Logic` | Logic (пользовательский) | Бизнес-логика объекта: методы поверх DPI | человек; генератор **не перезаписывает** |
| `Pub`   | Application View Interface | Пользовательский интерфейс: формы, операции, переопределения SQL | человек; генератор **не перезаписывает** |
| `Dpi`   | Data Provider interface | Системный слой данных: `<Obj>Obj`, get-/set- по атрибутам, имена таблиц | генератор; руками не трогать |
| `Dvi`   | Data View interface | Системный слой представления: базовые классы `DviDefault/DviList/DviCard/DviLookUp` | генератор; руками не трогать |
| `Pkg`   | Package | Вспомогательный сервис модуля (парсер, загрузчик, интеграция) | человек |

Первая строка `Logic`/`Pub` обязана содержать маркер, чтобы при открытии было
видно, можно ли файл править:

```python
# Пользовательский файл для логики     ← Logic
# Пользовательский файл для интерфейса ← Pub
# Системный файл для логики            ← Dpi (генерируется)
# Системный файл для интерфейса        ← Dvi (генерируется)
```

## 3. Классы внутри файлов

- Каждый класс наследует имя файла: `Awh_AnimeLogic.py` → `class Awh_AnimeLogic(Awh_AnimeDpi)`.
- Объект данных живёт в `Dpi`-файле и называется `<PREFIX>_<Object>Obj`:
  `Awh_AnimeObj` (в `Awh_AnimeDpi.py`).
- Вложенные классы интерфейса не дублируют префикс: `Awh_AnimePub.List`,
  `Awh_AnimeDvi.DviCard` — суффикс роли во вложенном имени не повторяется.
- Класс меню модуля: `<PREFIX>_MainMenuPub` (один на модуль, всегда в корне `object/`).

## 4. Каталоги

```
module/<mod>/
├── __init__.py              # публичный фасад: реэкспорт Logic/Pub/Pkg + __all__
├── README.md                # описание модуля, обязателен
├── config/
│   ├── app.json             # карточка модуля на экране выбора
│   └── hooks.json           # точки входа {on_startup: {name, isClassMetod}, ...}
├── schemas/<object>/        # метаданные объекта, три файла-компаньона:
│   ├── <P>_<Obj>.odb.json   #   структура БД (таблицы/атрибуты)
│   ├── <P>_<Obj>.Dmeta.json #   метаданные системного UI (caption, edit, order)
│   └── <P>_<Obj>.Ameta.json #   метаданные пользовательского UI
└── object/<object>/         # код объекта, каталог в нижнем регистре
    ├── <P>_<Obj>Dpi.py      #   системная логика (генератор)
    ├── <P>_<Obj>Dvi.py      #   системный интерфейс (генератор)
    ├── <P>_<Obj>Logic.py      #   пользовательская логика
    ├── <P>_<Obj>Pub.py      #   пользовательский интерфейс
    ├── <P>_<Obj>Pkg.py      #   (опц.) сервис объекта
    └── ...
```

- Каталог объекта — **нижний регистр**, имя объекта без префикса. Файлы внутри — с префиксом.
- Общие сервисы модуля (`*Pkg`) и `MainMenuPub` лежат непосредственно в `object/`,
  не в подкаталогах.
- Схема «папка = объект» одна для `schemas/` и `object/`: если есть
  `schemas/anime/`, код лежит в `object/anime/`.

## 5. Метафоры json-расширений

Расширение читается так же, как суффикс класса: `.odb` описывает данные,
`.Dmeta` — системный UI, `.Ameta` — пользовательский UI. Один объект — три файла
с одинаковым именем `<P>_<Obj>` и разными расширениями. Роль-маркеры должны
зеркалить друг друга (`Dpi ↔ .Dmeta`, `Logic ↔ .Ameta`).

## 6. Чего делать нельзя

1. **Никаких `utils.py`, `helpers.py`, `main.py`** внутри модуля —
   всё раскладывается по ролям; непонятно куда — значит, это новый `Pkg`.
2. Не создавать файлы без префикса модуля — они ломают вывод пакета в
   `ActionDispatcher` (`sNameClass[:find('_')]`) и коллизируют между модулями.
3. Не импортировать в `Logic/Pub` чужой модуль напрямую (`from module.<other>...`) —
   межмодульные вызовы только через `ActionDispatcherPkg().action("Cls.method")`
   или хуки в `hooks.json`.
4. Не редактировать `Dpi/Dvi` и их `.Dmeta.json` — при перегенерации изменения
   сотрутся; вся кастомизация идёт слоем выше (`Logic/Pub`, `.Ameta.json`).
5. Не класть в `__init__.py` ничего, кроме реэкспорта публичного API и `__all__`:
   этот файл — контракт модуля перед ядром (через него идёт диспетчинг хуков
   и `nameMainScreen` из `app.json`).

## 7. Чек-лист нового объекта

```bash
# имя объекта: Object, модуль: <mod>, префикс: <P>
mkdir -p module/<mod>/object/<object> module/<mod>/schemas/<object>
touch module/<mod>/object/<object>/<P>_<Object>{Logic,Pub,Dpi,Dvi}.py
touch module/<mod>/schemas/<object>/<P>_<Object>{.odb,.Dmeta,.Ameta}.json
# затем: добавить классы и объект в __init__.py (Logic/Pub), пункт меню в <P>_MainMenuPub
```

Проверка соответствия имени файла и класса:

```bash
f=module/<mod>/object/<object>/<P>_<Object>Logic.py
grep -q "class $(basename $f .py)" $f && echo OK || echo "ИМЯ != КЛАСС"
```
