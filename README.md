# NecoTab

Модульная платформа, где **каждый модуль — самостоятельное приложение**. Приложение
открывается и в браузере, и как десктопное окно, ощущаясь именно как приложение,
а не как сайт.

---

## Стек

| Слой | Технология | Зачем |
|---|---|---|
| Сервер / API | **FastAPI + Uvicorn** | REST-эндпоинты данных и операций, хранилище (libsql/Turso) |
| Шаблоны | **Jinja2** | серверный рендеринг HTML из метаданных (schema-driven UI) |
| Интерактив | **HTMX** | подгрузка фрагментов страницы и вызов `@Oper`-операций без JS-сборки |
| Локальный UI-стейт | **Alpine.js** | мелкие клиентские состояния (меню, модалки, фильтры на лету) |
| Push-обновления | **SSE** (Server-Sent Events) | события с сервера «как WebSocket», но проще |
| Каркас | **App Shell** | единый HTML-каркас (шапка, боковая панель, контент), HTMX подгружает только фрагменты |
| Десктоп | обёртка над веб-UI (например, pywebview) | локальный FastAPI-сервер + нативное окно |

**Офлайн-режим и локальный SQL на клиенте не нужны** — вся работа через API.
От Qt отказались: он был только для прототипирования.

Возможна миграция фронтенда (React/Vue) без переписывания логики: контракт системы —
метаданные (`Dmeta/Ameta`) и реестр операций (`@Oper`), а не конкретный фреймворк.

## Архитектура

### Слои

```
core/                 # ядро: генератор классов, ActionDispatcher, БД, мета-классы
webapp/main.py        # FastAPI: API + рендеринг UI
module/<mod>/         # модули-приложения (сейчас в репозитории: bc)
```

### Модель взаимодействия

UI нигде не дергает `Pkg` или `Logic` напрямую. Всё взаимодействие:

- **только через `@Oper`-методы** (операции, объявленные в `Pub`) и сеттеры;
- диспетчинг — через `ActionDispatcher` (`ACTIONDISPATCHER.getClassByName(...)`,
  `.action("Cls.method")`).

Классы-строители UI:

- **Dvi** — системный слой представления (генерируется): базовые классы
  `DviDefault / DviList / DviCard / DviLookUp`;
- **Pub** — пользовательский слой: формы, операции (`@Oper(label=..., order=...)`),
  переопределения SQL;
- метаданные описываются схемами `attrMetaSchema / filterMetaSchema / metaSchema`
  (`core/dataClass/metaDataClass.py`) и json-файлами `.Dmeta` / `.Ameta`.

Из метаданных сервер генерирует таблицы, формы и карточки — **schema-driven UI**:
ручной вёрстки форм нет.

### Структура модуля

```
module/<mod>/
├── __init__.py              # публичный фасад модуля (реэкспорт + __all__)
├── README.md                # описание модуля
├── config/
│   ├── app.json             # карточка модуля (name, nameMainScreen)
│   └── hooks.json           # точки входа модуля
├── schemas/<object>/        # <P>_<Obj>.odb.json / .Dmeta.json / .Ameta.json
└── object/<object>/         # код объекта: Logic / Pub / Dpi / Dvi / Pkg
```

Полное соглашение об именовании — в [CONVENTION_MODULE_NAMING.md](CONVENTION_MODULE_NAMING.md).
План развития — в [ROADMAP.md](ROADMAP.md).

## Запуск

Требования: **Python ≥ 3.12**.

```bash
pip install -r requirements.txt

# 1. Настройка БД (config.json не хранится в git — секреты)
cp core/config/config.example.json core/config/config.json
# и укажите в нём database.url и database.auth_token (libsql/Turso)

# 2. Запуск сервера (http://127.0.0.1:8000)
python main.py launchServer
```

Для сессий можно задать свой секрет: `export SESSION_SECRET=...`
(иначе используется dev-значение из `webapp/main.py` — только для локального запуска).

### Вспомогательные генераторы (код-генерация)

```bash
python main.py createSours <путь>    # сгенерировать исходники объекта (таба)
python main.py createClass <путь>    # создать класс-объект (таб)
python main.py createModule          # создать модуль (sys / «система»)
```

Без аргументов `main.py` запускает `createTab` по умолчанию — это convenience-режим
разработки, путь в нём захардкожен под машину автора и может быть неактуален.

### Тесты и проверки

```bash
pytest                      # тесты (см. tests/README.md)
ruff check .                # линтер
black .                     # форматирование
mypy .                      # типы
# или интерактивное меню: dev.bat (Windows)
```

Десктопный режим — запуск того же веб-интерфейса в нативном окне-обёртке (`LAUNCH APP.cmd`,
ожидает локальный Python в `./python/`) — **в планах**, контракт CLI `launchApp` ещё не реализован в `main.py`.

## Как это работает в рантайме

1. Браузер загружает **App Shell** — один раз, дальше навигация без перезагрузки страницы.
2. HTMX тянет из сервера **фрагменты** (список, карточка, форма), отрендеренные Jinja2
   из метаданных объекта.
3. Кнопки/действия в UI = вызовы `@Oper`-методов через эндпоинты вида
   `POST /action/{oper}` (операции формы) и `GET /{menu}/{form}/action/{oper}`
   (операции главного меню) — с whitelist-проверкой `getSetterAndOperName()`,
   прямого доступа к логике нет.
4. SSE-поток (`GET /events`, `sse-starlette`) доставляет события (обновление данных,
   прогресс длительных задач) «как WebSocket».
5. Межмодульные вызовы — только через `ActionDispatcher.action("Cls.method")` и хуки.

## Принципы

- **Модульность**: новый модуль подключается добавлением папки в `module/` и записью в `project.yaml`.
- **Метаданные — контракт**: меняешь `.Dmeta/.Ameta` — меняется UI, код писать не нужно.
- **Изоляция слоёв**: UI → только `@Oper`/сеттеры; логика → `Logic/Pkg`; данные → `Dpi` + БД.
- **Без сборки**: HTML/JS без bundler'ов; Alpine/HTMX подключаются как статика.
